    Memory 系统设计的一些要领

    2026-11-22 · 发布于 文章 · 6334 字 · 13 分钟
    • AI
    • Memory
    • AI Agent
    • 系统设计
    • RAG

    给 Agent 加记忆，最容易想到的做法是：把对话切块、算 embedding、存进向量库，查询时取 top-k 塞回上下文。这个 demo 通常一个下午就能跑通。

    但把它放到真实产品里，问题会从各个方向冒出来：同一件事被记了三遍；用户上个月说喜欢 A，这个月改成了 B，召回时两条一起出现；检索结果看起来都相关，拼进上下文却互相矛盾；多租户之后，A 租户的记忆出现在 B 租户的召回里；月底对账，LLM 调用量比写入量高出一个数量级。

    这些问题说明，Memory 不是一个"检索接口"，而是一条从写入、整理、召回到评测和治理的完整链路。写入决定"记得对不对"，召回决定"取得准不准"，评测决定"有没有变好"，平台化决定"能不能规模化"。下面按这条链路，把从零到一做 Memory 时真正需要想清楚的事情拆开讲。

    一、先定数据形态：证据层与事实层

    第一件事不是选向量库，而是决定"记忆以什么形态存在"。

    一个比较稳妥的做法是同时保留两层：

    层次存什么作用丢失的代价
    证据层原始 session / turn，逐字保留可回放、可审计、可重新抽取抽取器升级后，历史无法重算
    事实层抽取、去重后的短句 insight直接参与召回召回质量下降，但证据还在

    只存事实，抽取模型一换代，历史数据就永久定型了；只存原文，每次召回都要实时理解，延迟和成本都不可控。所以更合理的顺序是"先存证据，再抽事实"：证据层负责完整，事实层负责好用。

    两层之间的写入策略也要提前定。证据层可以尽力而为，丢了不影响事实层的正确性；事实层则要从严，写错或重复的代价远高于少写一条。这个不对称，会贯穿后面所有的失败处理。

    写入入口通常不止一个，至少要想清楚三类：

    • messages 智能摄取：传入一轮或多轮对话，由服务端抽取事实并整理；
    • content 直写：调用方已经想清楚要记什么，原文直接成为一条记忆；
    • pinned 显式钉住：用户明确要求长期保留的内容。

    pinned 不是普通记忆加个标记，它在后续的自动整理中需要被保护：不能被自动 UPDATE 覆盖，也不能被 DELETE 删除。用户显式意图的优先级要高于自动对账。

    二、写入链路：难点不在存，而在整理

    2.1 同步还是异步

    LLM 抽取是秒级到分钟级的操作，把它放在同步请求里，接口很快会超时。更常见的做法是默认异步：请求返回 202，后台任务完成抽取和对账，调用方通过状态接口查询结果；同时保留一个同步开关，给小数据量、测试和调试使用。

    异步化之后，几个工程问题必须一起解决：

    • 幂等：同一批 messages 被重放时不能重复写。幂等键通常用 session_id 加内容 hash，或者由调用方显式传入；
    • 重试与死信：LLM 超时、限流、返回非法 JSON 都要能重试，重试耗尽后进入死信队列，而不是静默丢失；
    • 状态机：任务要有 pending / running / complete / partial / failed 这类明确状态，调用方和运维都要能看懂；
    • 超时：同步模式要设上限，异步模式要有整体 deadline，不能让一个任务无限挂起。

    2.2 抽取：比"记什么"更重要的是"不记什么"

    抽取通常一次 LLM 调用同时产出事实、类型、标签、来源消息序号和时间信息。prompt 里写得最清楚的往往是"要抽什么"，但实际决定记忆库质量的，是过滤规则。

    用户说"帮我查一下明天的天气"，这是一次性意图；说"我现在在开会"，这是临时状态；说"刚跑完一个测试"，这是操作日志。这些内容如果都进长期记忆，记忆库很快会被噪声淹没。所以需要一个明确的过滤层：

    • 按事实类型过滤：一次性意图、临时状态、操作日志直接丢弃；
    • 按角色过滤：system、tool 通常不参与抽取，assistant 是否参与要显式决定；
    • 按长度和数量过滤：输入截断，单次产出设上限，防止 token 爆炸；
    • 用规则兜底：LLM 没给类型或给了未知类型时，用正则和中英文关键词做最后一道闸。

    过滤规则要可观测：每类过滤各丢了多少条，应该成为指标。否则线上出现"记忆变少"时，很难判断是抽取退化还是过滤过严。

    2.3 对账：Memory 系统的分水岭

    如果只做 ADD，系统会不断膨胀：同一实体、同一属性被反复记录，召回时全是近似重复项。真正难的是对账，也就是把新事实和既有记忆放在一起，决定新增、更新、删除还是忽略。

    成熟的实现通常会定义四种动作：

    动作语义关键规则
    ADD新信息，或同一实体的不同属性产出新的记忆和标签
    UPDATE同一实体、同一属性槽的替换必须能定位旧记忆，并保留原文用于校验
    DELETE明确矛盾时才删除不因为新事实更简略就删除旧事实
    NOOP已被既有记忆覆盖不需要返回，避免无效写

    对账流程里有几个容易被低估的细节：

    1. 候选生成。对每条新事实召回 top-k 既有记忆，相似度低于阈值直接丢弃，避免把无关内容塞进 LLM 上下文。候选太多会让模型分心，候选太少又容易漏掉真正需要更新的记忆。
    2. ID 映射。不要把真实 UUID 直接交给 LLM，模型很容易编造或抄错。更稳的做法是把候选映射成连续的整数，让模型只引用整数，执行时再映射回真实 ID。
    3. 时间标注。给候选附上相对年龄，比如"两个月前"。很多冲突不是语义冲突，而是时间冲突；没有时间信息，模型无法判断哪条更新。
    4. pinned 保护。对 pinned 记忆，UPDATE 可以降级为 ADD，DELETE 直接拒绝。
    5. 失败语义。对账 LLM 失败或 JSON 解析失败时，宁可整批跳过，也不要退化成"全部当新增"。后者会产生大量重复记忆，而且很难事后清理。

    这也是 ADD-only 方案和完整对账方案的核心区别：前者实现简单，但把整理成本推给了召回和用户；后者写入更重，却能让记忆库随时间保持收敛。

    2.4 更新与删除：原地改，还是追加归档

    UPDATE 有两种实现方式，取舍不同：

    • 原地 upsert：同一行更新内容和版本号，存储省，但历史丢失；
    • 追加归档：新内容写新行，旧行原子归档，历史完整，但存储和扫描量更大。

    如果产品需要审计、回溯，或者要让用户看到"这条记忆是怎么变的"，追加归档更合适。删除则建议软删，用 state 字段区分 active / archived / deleted，检索侧统一过滤。物理删除很难恢复，也不利于排查问题。

    2.5 一个容易被忽略的坑：记忆自污染

    很多 Agent 插件的工作方式是：先召回记忆，把结果拼进上下文，再把整轮对话上传回 Memory 服务。如果服务端不处理，这些召回内容会被当成新的对话再次抽取，形成"记忆里套记忆"。

    所以写入前需要有一个净化步骤，把注入的上下文片段剥掉。这个细节看起来小，但一旦漏掉，记忆库会以肉眼可见的速度膨胀，而且内容越来越像自我复读。

    2.6 失败语义要提前约定

    写入链路的每一步都可能失败，提前约定"哪些失败可以继续、哪些必须终止"，比事后补日志有用得多。

    失败点建议行为理由
    参数校验终止，返回 4xx调用方错误，重试无意义
    证据层落库记录日志，继续证据可丢，事实层仍可工作
    抽取失败终止整条流水线事实错了，后面全错
    对账候选检索全失败终止，不降级为全新增防止静默重复写入
    对账 LLM 失败跳过全部动作，返回 partial宁可少写，不可重复写
    单条动作失败记录 warning，继续其余动作部分成功好于整体失败
    配额提交失败同步返回错误，异步记日志计量不能静默丢失

    核心原则只有一句：证据层尽力而为，事实层从严。

    三、召回链路：过滤在前，融合在中，组装在后

    3.1 Scope 过滤必须先做

    召回的第一件事不是算相似度，而是确定"哪些记忆有资格被看到"。租户、应用、Agent、空间、状态（active）、是否有 embedding，这些条件都应该进入 SQL，而不是查出来再过滤。

    原因有两个：一是安全，后过滤很容易在分页、缓存、重排环节漏掉；二是性能，先缩小候选集，后面的向量计算和重排才有意义。

    3.2 多路召回与融合

    单一向量检索并不够。向量擅长语义相似，但对人名、代号、错误码、配置项这类精确匹配反而不稳定；反过来，全文检索擅长精确词，却不懂同义表达。

    比较稳的做法是几路并行：

    • 向量检索：语义相近的记忆；
    • 全文/关键词检索：精确的人名、项目名、错误码；
    • 标签与元数据：按主题、来源、时间过滤；
    • 时间通道：最近发生的事实，或者与查询时间相关的事实。

    每一路多取一些候选（比如目标条数的三倍），再用 RRF 这类排名融合算法合并。RRF 的好处是不需要把不同通道的分数校准到同一量纲，工程上更稳。

    3.3 打分不能只看相似度

    相似度高不代表应该被召回。实际排序通常还要叠加：

    • 时效：新事实优先，尤其是状态类信息；
    • 重要度：pinned、用户显式标记、高频访问的记忆加权；
    • 置信度：来源可靠、被多次确认的事实加权；
    • 时间感知：区分"当前事实"和"历史事实"，避免旧结论压过新结论。

    如果记忆里同时存在"用户喜欢 A"和"用户改喜欢 B"，召回应该能判断后者更新，而不是把两条并列塞给模型。

    3.4 重排、去冗余与上下文组装

    融合后的 top N 还可以做一次重排，用 cross-encoder 或小模型判断"这条记忆对当前问题是否真的有用"。重排的收益通常比继续调召回阈值更明显，但要注意延迟预算。

    重排之后还要去冗余。近似重复的记忆同时出现，会浪费上下文窗口，也会让模型误以为这件事被多次确认。可以用 MMR 或相似度阈值做多样性控制。

    最后的上下文组装，建议给"证据"而不只是"结论"：一条事实配上它来自哪轮对话、什么时候说的。这样模型在遇到冲突时，才有机会做进一步判断。

    3.5 延迟预算与降级

    召回是在线链路，必须有明确的延迟预算和降级顺序：

    • 向量检索失败，退到全文检索；
    • 重排失败，跳过重排直接用融合结果；
    • LLM 改写失败，用原始 query；
    • 所有通道都失败，返回空结果，而不是报错拖垮整个请求。

    空召回也要足够便宜。很多请求本来就不需要记忆，如果每次都要走完整条链路，成本会被放大。

    3.6 反馈闭环

    召回系统最缺的往往不是算法，而是标注。哪条记忆被真正引用了、哪条被用户否定了、哪条召回后模型仍然答错，这些信号比离线数据集更真实。

    可以先把"记忆是否出现在最终回答的引用里"作为弱信号，再逐步引入显式反馈。这些数据既能调权重，也能反哺写入侧的过滤和对账。

    四、怎么证明它有效

    Memory 系统的评测不能只看"召回了几条"。至少要分三层：

    层次指标关注点
    组件级recall@k、precision、MRR、nDCG检索通道本身是否准
    端到端QA 准确率、任务成功率、多轮一致性记忆是否真的帮模型答对
    系统级p50/p95/p99 延迟、token 开销、单次成本、吞吐是否可用、是否用得起

    4.1 写入质量要单独评

    只评召回，会掩盖一个事实：如果库里全是重复和过期内容，top-k 看起来再相关，端到端效果也不会好。

    写入侧至少要看：

    • 事实准确率：抽出来的事实是否忠于原文；
    • 重复率：同一实体、同一属性是否被反复写入；
    • 过期事实率：旧结论是否被正确更新或归档；
    • 动作正确率：UPDATE / DELETE 是否打在了正确的记忆上；
    • 过滤命中率：该丢的噪声是否被丢掉。

    4.2 数据集要覆盖"难"的部分

    简单的单轮问答测不出 Memory 的价值。更有意义的样本通常包含：

    • 多 session、长时间跨度；
    • 事实随时间演化，前后矛盾；
    • 大量干扰会话，只有少数内容与问题相关；
    • 负样本：某些内容明确不应该被记住；
    • 跨语言、跨领域的表达差异。

    4.3 方法论：baseline、A/B 与灰度

    评测最重要的是可比性。同一个模型、同样的温度、同样的工具集，只切换"有记忆"和"无记忆"两个 profile，跑同一批样本，才能把收益归因到 Memory 上。

    具体做法可以分三层：

    1. 离线回归：固定 golden set，每次改动都跑，防止指标回退；
    2. 线上 A/B：按用户或会话分流，观察任务成功率、追问次数、用户反馈；
    3. Shadow 模式：新策略先只观测不生效。比如近重复抑制，可以先记录相似度分布，验证阈值后再真正拦截。

    4.4 别忽略负向指标

    除了"答对了多少"，还要看"因为记忆答错了多少"：

    • 错误记忆导致的幻觉；
    • 过期事实被当成当前事实；
    • 跨租户、跨 scope 的记忆泄漏；
    • 召回内容过长导致的上下文挤占。

    这些指标往往比准确率更能反映系统是否可上线。

    五、从单机到云平台

    当 Memory 从"一个服务"变成"一个平台"，需要考虑的事情会多一个数量级。

    5.1 租户与隔离

    先决定隔离级别：

    • 逻辑隔离：共享库表，用 tenant_id 做行级隔离，成本低，但需要严格的查询约束和防越权测试；
    • 物理隔离：独立库、独立 schema 或独立连接池，隔离性好，但 provisioning、迁移和资源调度更复杂。

    无论选哪种，都要想清楚租户生命周期：创建、初始化、暂停、导出、删除。删除尤其麻烦，要确保数据、索引、缓存、备份都被清理。

    5.2 Scope 与权限

    租户之下通常还有层级：应用、Agent、空间、链。scope 既是安全边界，也是召回过滤条件。权限模型至少要区分：

    • 认证：API Key、Agent ID、服务身份；
    • 授权：读、写、删、共享、跨空间可见性；
    • 审计：谁在什么时候读了哪条记忆，谁删了什么。

    API Key 的轮换、吊销和最小权限，也要在早期设计进去。

    5.3 配额与计量

    云平台的配额不是简单的计数器，而是一个租约模型：

    1. 请求开始时先 Reserve 预留额度；
    2. 成功后 Commit，失败后 Release；
    3. 进程崩溃或超时要有兜底，避免预留泄漏成永久占用。

    计量维度通常包括：写入次数、读取次数、存储量、LLM token、embedding 调用。还要明确 fail-closed 还是 fail-open：配额服务不可用时，是拒绝写入，还是先放行后补记。

    计量本身要幂等，异步刷写建议走 outbox，避免因为一次网络抖动丢账单。

    5.4 可靠性与限流

    • 限流至少分两层：按 IP 防刷，按租户或 API Key 防单租户打满；
    • 异步链路要有背压，队列满时明确拒绝或降级；
    • 外部依赖（LLM、embedding、向量库）要有超时、重试和熔断；
    • 死信队列要可查询、可重放，不能成为黑洞。

    5.5 可观测性

    Memory 系统的可观测性要覆盖同步和异步两条链路：

    • request_id 贯穿请求、后台任务、webhook 和计量；
    • HTTP 层看 RED 指标，资源层看 USE 指标；
    • 流水线分阶段打点：净化、证据落库、抽取、对账、路由各花了多久；
    • 每租户看板：写入量、召回量、错误率、配额余量；
    • 数据质量指标：重复率、过滤率、对账动作分布、空召回率。

    没有这些指标，线上出现"记忆变差"时基本无法定位。

    5.6 数据生命周期与合规

    • 保留策略：哪些数据多久清理，原始对话和事实是否同样对待；
    • 用户数据导出与删除：删除要传播到向量索引、缓存和备份；
    • 加密：传输加密、静态加密、密钥管理；
    • PII：写入前脱敏，或者至少提供可配置的脱敏规则；
    • 备份与恢复：恢复演练要包含向量索引和元数据的一致性。

    5.7 成本

    Memory 的隐性成本主要不在存储，而在 LLM。每次写入都可能触发抽取和对账，调用量会远高于写入请求数。

    可控的手段包括：抽取用便宜模型、对账用更强模型；批量合并请求；对低价值内容提前过滤；按租户设预算和采样率。成本模型最好在早期就建立，否则用户量上来后再优化会很被动。

    六、落地顺序

    如果从零开始，比较稳的顺序是：

    1. 证据层 + 直写 + 混合召回：先把"存进去、取得出"的闭环跑通，不急着上 LLM；
    2. LLM 抽取：在闭环上增加事实层，同时建立过滤规则和指标；
    3. 对账：加入 UPDATE / DELETE / NOOP，解决重复和过期问题；
    4. 评测体系：离线 golden set、baseline A/B、shadow 观测；
    5. 平台化：多租户、scope 权限、配额计量、可观测和数据生命周期。

    这个顺序的好处是，每一步都能独立验证。反过来，如果一开始就同时做对账和多租户，很容易在没有评测基线的情况下优化错方向。

    Memory 系统的护城河，通常不在向量库选型，而在写入质量、评测闭环和平台治理。向量检索只是其中最容易被替换的一环。

    本文参考 Memory9（mem9）的实现进行总结。
