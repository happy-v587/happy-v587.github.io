    为什么会有这篇文章

    @earendil-works/pi-tui 是从 earendil-works/pi 里拆出来的终端 UI 组件库。Pi 是那个九万多 star 的 AI 编程工具集，它界面上跑着的这套东西，就是 pi-tui 在画。

    用它的感觉，像是在终端里装了个超小号的 React。你不拼 ANSI 转义序列，而是搭一棵组件树；状态一变，库自己算出哪几行要改再写屏。换行、对齐、中文宽度、输入法光标这些琐事都有人管了。

    它替你拦下了三类脏活：

    • 组件树，Text、Box、Markdown、Input、SelectList 这些挂在 TUI 根节点下；
    • 差分渲染，每次只重画变化的部分，不会整屏闪；
    • 输入路由，按键分发给当前聚焦的组件。

    快速上手

    新建一个 Node.js（>=22.19）TypeScript 项目，装包跑起来：

    mkdir my-tui-app && cd my-tui-app
npm init -y
npm install @earendil-works/pi-tui typescript tsx @types/node

    写个最简单的入口 src/main.ts：

    import { Key, matchesKey, ProcessTerminal, Text, TuiMainScreen } from "@earendil-works/pi-tui";

const terminal = new ProcessTerminal();
const tui = new TuiMainScreen(terminal);

tui.addChild(new Text("\x1b[36m你好，pi-tui\x1b[0m")); // ANSI 青色

tui.addInputListener((data) => {
  if (matchesKey(data, Key.escape) || matchesKey(data, Key.ctrl("c"))) {
    tui.stop();
    process.exit(0);
  }
  return { consume: true };
});

tui.start();

    运行：

    npx tsx src/main.ts

    按 Ctrl+C 或 Esc 退出。

    核心概念

    TUI 接口和两种渲染器

    TUI 是接口类型，不是类。刚上手最容易在这里卡住：直接 new TUI() 会当场报错。你得在下面两个渲染器里挑一个，把变量类型标成 TUI。

    渲染器mode适用场景
    TuiMainScreenregular内容渲染在主屏，保留在终端滚动历史里，适合 chat / 日志流式输出
    TuiAltScreenfullscreen进入备用屏幕缓冲区，全屏接管、滚动由应用自己管理，适合编辑器
    const tui: TUI = new TuiMainScreen(terminal);   // 默认
// const tui: TUI = new TuiAltScreen(terminal);  // 全屏模式

    TuiAltScreen 是 ViewportTUI，布局逻辑和主屏差挺多，下面单独说。

    生命周期方法：

    tui.addChild(comp);     // 挂组件
tui.removeChild(comp);  // 摘组件
tui.clear();            // 清空所有子节点
tui.setFocus(input);    // 把焦点交给某个 Focusable 组件
tui.requestRender();    // 请求一次重渲染（改文案后调用）
tui.renderNow(true);    // 立即强制重渲染
tui.showOverlay(comp, options);  // 弹浮层，返回 OverlayHandle
tui.hideOverlay();      // 收起最顶层浮层
tui.addInputListener(fn); // 全局键盘监听，返回取消函数
tui.start();            // 启动
tui.stop();             // 停止

    TuiAltScreen 与布局根（ViewportTUI）

    TuiAltScreen 是 ViewportTUI，可以拿 isViewportTUI() 辨别。它和主屏的根本差别，在于滚动区归谁管。

    TuiMainScreen 把内容直接写到终端主屏，超出一屏会自动滚进终端自带的滚动历史（scrollback），所以它只要 render(width) 输出一块「文档」，高度的事终端兜底。

    TuiAltScreen 不一样。它进入备用屏幕（ESC[?1049h）后先清屏、关掉自动换行，整个工作台就是终端那 rows 行，没有滚动历史可以掉进去。谁占几行、往哪里滚，必须由应用自己说了算。因此有两种用法：

    不调 setLayoutRoot。 你用 addChild 挂上去的子组件，会被自动包进一个内置的主 ScrollView（follow: "end"），整棵组件树当一块文档滚动。一个滚动条，PageUp / PageDown、搜索都作用在这块文档上。聊天这种自上而下的流式场景，最省事。

    调 setLayoutRoot()。 你把一棵由 VStack / HStack / ScrollView 组成的布局树设成唯一根节点。布局引擎 renderLayoutFrame 按 flexbox 语义给每个区域分配行列，ScrollView 各自认领自己的子区域做滚动。这样才能让多块可滚动区共存：滚轮事件按指针坐标路由到对应的 ScrollView，配合 overscroll: "chain" 把溢出链式传给下一个区域或主视口。

    源码里能直接看到这个分支（tui-alt-screen.js）：

    setLayoutRoot(root) { this.layoutRoot = root; this.currentLayout = undefined; this.requestRender(); }
render(width) { return this.layoutRoot?.render(width) ?? super.render(width); }
// doRender 里真正的渲染根：
const root = this.layoutRoot ?? this.implicitScrollView;

    implicitScrollView 就是兜底那层内置主滚动视图。一句话：主屏让终端替你滚动，全屏得亲手分配每一行。要么接受内置的单文档，要么上布局树。

    Component 接口

    所有组件都实现它：

    interface Component {
  render(width: number): string[];  // 给定视口宽度，返回一组终端行
  invalidate(): void;               // 失效缓存，下次强制从零重画
  handleInput?(data: string): void; // 可选：组件聚焦时接收键盘输入
}

    render 这三个方法背后其实叠了三件事：

    • 返回的行是字面字符串
    • TUI 做行级 diff
    • 组件按内容缓存

    一行字面字符串。 快速上手里那个青色例子，Text 拼出来的一行，就是这个字面量的原样（后面再补空格到整行宽）：

    \x1b[36m你好，pi-tui\x1b[0m

    \x1b[36m 是个 ANSI 转义序列：ESC [ 开头，36m 表示把前景色置成青色，之后的字符都生效；\x1b[0m 把样式复位。终端收到这些序列只改样式、不占显示位，所以字符数和显示列数对不上：你好 和全角逗号各占两列，加 ASCII 的六列，一行九个字符占十二列。宽度统一用 visibleWidth() 算，换行、补位、对齐都拿它当标准，不会把 \x1b[...m 这部分数进去。

    行级 diff。 TUI 每次渲染，把这帧的所有行和上一帧逐行比。假设帧里只有三行，焦点从选项 A 移到选项 B：

    上一帧（previousLines）：

    菜单
> 选项 A
  选项 B

    再渲染一帧：

    菜单
  选项 A
> 选项 B

    逐行比下来只有第 2、3 行不同（firstChanged = 1、lastChanged = 2，0 起算），于是光标挪到第 2 行，\r\x1b[2K 清这两行重写，第 1 行纹丝不动。真实的行里带着 ANSI 样式序列，diff 比的就是完整字符串，样式变了也算变化。

    按「内容 + 宽度」缓存。 每次 doRender 都会把整棵树跑一遍，每个组件都调一次 render(width)。Text、Markdown 这类组件把拼好的行存起来，键是「内容 + 宽度」：内容和宽度都没变就原样返回，否则重拼。缓存这层其实挺聪明，内容变了它是能自己发现的。

    麻烦点在干净利落地把结论说出来有点绕。缓存只保证「下次有这一帧时，能拿出新内容」，但它不保证「一定会有这一帧」。出帧是 TUI 的决定：requestRender() 打上 dirty 标记，安排一次 doRender。清缓存和出新帧，是两件分开的事：

    title.setText("新标题");  // ① 让组件忘掉旧缓存，下次渲染拿得出新内容
tui.requestRender();      // ② 安排一帧：跑树 → diff → 写屏

    对照「画面不动」的两种可能：只做 ①，setText 本身不触发渲染，dirty 没置位，帧根本不安排，屏幕就停在旧画面上；只做 ②，组件缓存键恰好没变（常见于自己写的组件、或绕过 setter 直接改了内部状态），返回的还是旧行，diff 一比毫无差异，等于没画。所以自定义组件改完内部状态记得 .invalidate() 清缓存。排查「改了没反应」，先问自己：缓存清了没，帧安排了没。

    Container 与组合

    Container 是个啥都能装的容器，TuiBase（两个 TUI 的基类）本身就是个 Container：

    const box = new Box(paddingX, paddingY, backgroundFn);
box.addChild(new Text("..."));

    Focusable（给输入法用的）

    组件要和输入法协作的话，实现 Focusable，TUI 切焦点时会帮你把 focused 字段置好。聚焦时组件在光标位置埋一个 CURSOR_MARKER 标记，TUI 定位后立刻剥掉，再把硬件光标挪过去，输入法候选框就出现在正确位置了。Input 和 Editor 已经内置。

    主题与 ANSI 样式

    所谓主题，其实就是一个 (text: string) => string 的函数，往里塞 ANSI 就行。demo 里常用的几个：

    const style = (code: string) => (text: string) => `\u001b[${code}m${text}\u001b[0m`;
const bold = style("1");     // 加粗
const dim  = style("2");     // 暗色
const cyan = style("36");    // 青色前景
const green = style("32");
const yellow = style("33");
const blue = style("34");
const magenta = style("35");
const selected = style("1;30;46");                 // 加粗黑字 + 青色背景 = 选中态
const panelBg = (t: string) => `\u001b[48;5;236m${t}\u001b[49m`; // 256 色背景块

    Box 的第三个参数、Text 的第四个参数，以及 Markdown / SelectList 的 theme，全是这类函数。

    常用组件

    Text

    import { Text } from "@earendil-works/pi-tui";

// Text(内容, 水平 padding, 垂直 padding, 背景函数)
const hello = new Text("Hello", 1, 0);
hello.setText("新的内容");   // 动态改文案

    多行，按可见宽度自动断行，中英文宽度都算对了，ANSI 保留不破坏。动态内容用 setText。

    Box

frame.addChild(new Text("标题"));

    给子组件加内边距和背景。背景函数会把整行铺满到视口宽度，出来的效果就是一个色块面板。

    Spacer

    import { Spacer } from "@earendil-works/pi-tui";

tui.addChild(new Spacer(1));  // 空 1 行

    留白，仅此而已。

    TruncatedText

    import { TruncatedText } from "@earendil-works/pi-tui";

new TruncatedText("这一条很长很长...", 1, 0);

    超宽不换行，右边加省略号。状态栏、路径、文件名单行展示都合适。

    Markdown

    先配一个 MarkdownTheme：

    import { Markdown, type MarkdownTheme } from "@earendil-works/pi-tui";

const theme: MarkdownTheme = {
  heading: bold, link: blue, linkUrl: dim,
  code: yellow, codeBlock: green, codeBlockBorder: dim,
  quote: magenta, quoteBorder: dim, hr: dim, listBullet: cyan,
  bold, italic: style("3"), strikethrough: style("9"), underline: style("4"),
};

// Markdown(内容, paddingX, paddingY, theme)
const md = new Markdown("## 标题\n\n支持 **粗体**、`代码`、[链接](https://...) 和列表", 1, 0, theme);

    标题、粗体、斜体、删除线、行内代码/代码块、引用、分割线、列表、表格（单元格按宽度换行）都有。MarkdownOptions 里能开 renderLatex（默认开，把 LaTeX 数学公式转成 Unicode）和 transform（渲染前按可用宽度改写源文）。

    Loader / CancellableLoader

    const loader = new Loader(tui, cyan, dim, "正在加载...");
loader.start();        // 开始转圈动画
loader.stop();         // 停止
loader.setMessage("换个文案");

    前两个参数是指示器颜色和消息颜色，Loader 其实是 Text 的子类。动画帧可配 { frames: [...], intervalMs: 80 }，frames 传空数组就只显示文案。CancellableLoader 追加了 Esc 取消，暴露 loader.signal（AbortSignal），用户按 Esc 时 onAbort 触发。

    内置 ↑/↓、/ 或直接输入过滤、智能选中、滚动提示、宽度不足自动截断、label 和 description 双列对齐。onSelectionChange / onSelect / onCancel 三个回调覆盖移动、确认、取消。

    VStack / HStack / ScrollView（只有 AltScreen 有）

    这几个是显式布局组件，TuiMainScreen 上没有，它信终端自己的滚动历史。

    import { VStack, HStack, ScrollView, Text } from "@earendil-works/pi-tui";

const vstack = new VStack([txt1, new ScrollView(txt2, { follow: "end" })], { gap: 1 });
tui.setLayoutRoot(vstack); // 仅 TuiAltScreen

    StackChild 可以是纯组件，也可以是 { component, basis, grow, shrink, minSize, maxSize, visible }，flexbox 语义。StackOptions 有 gap 和 align。ScrollView 包住一个子组件，scrollbar: "auto" 就有滚动条，scrollTo / scrollBy / scrollToStart 控制滚动，follow: "end" 自动贴底。

    Overlay 浮层

    showOverlay 在现有内容之上叠一个组件，对话框、菜单这类东西很合适。

    handle = tui.showOverlay(dialog, {
  width: "60%",            // 支持百分比
  maxHeight: "50%",
  anchor: "center",        // 九个锚点之一
  margin: 2,
  visible: (w, h) => w > 60,  // 条件显示
});
handle.hide();          // 永久移除
handle.setHidden(true); // 临时隐藏
handle.focus();         // 聚焦浮层
handle.unfocus();       // 释放焦点
tui.hideOverlay();      // 收起最顶层

    width、maxHeight、row、col 都支持百分比，anchor 有九个锚点，visible 回调能按终端尺寸决定显不显示。handle.hide() 永久移除，setHidden 临时切换。

    键盘事件

    全局监听注册在 tui.addInputListener 上，返回值决定事件是否被消费：{ consume: true } 短路，不再往下传；{ data } 可以改写原始输入再交给下一个；undefined 就继续递给聚焦组件。

    用 matchesKey + Key 匹配按键，自动兼容 Kitty 键盘协议：

    import { Key, matchesKey } from "@earendil-works/pi-tui";

matchesKey(data, Key.escape);            // Esc
matchesKey(data, Key.ctrl("c"));         // Ctrl+C
matchesKey(data, Key.ctrlShift("p"));    // Ctrl+Shift+P
matchesKey(data, Key.pageUp);            // PageUp
matchesKey(data, Key.super("k"));        // Super+K（Cmd+K）

    符号键也有命名：Key.backtick、Key.period、Key.slash。parseKey 能拿回键标识字符串。Kitty 生效时还能用 isKeyRelease / isKeyRepeat 判断事件类型。

    底层机制

    想知道它为什么不闪烁、为什么这么快，值得把源码翻出来看。下面都以 demo 锁定的 0.84.4 为例，文件在 node_modules/@earendil-works/pi-tui/dist/。

    分层

    进程 stdin/stdout
   │
ProcessTerminal      终端层：raw mode、按键字节流解析、Kitty 协议协商、屏幕控制序列
   │
TuiBase (TUI)        渲染调度 + 差分对比 + 输入路由 + 焦点 + 浮层栈
   │
Container / 组件树   render(width) -> string[]  每行是一段带 ANSI 的文本

    数据流是单向的：组件只声明自己长什么样，写屏永远由 TUI 负责。组件之间不能互相写终端，输出才可控、可 diff。

    渲染模型：宽度驱动 + 行缓存

    Component.render(width) 收终端列数，还一组终端行。一行就是一段带 ANSI 的字面字符串，宽度用 visibleWidth() 量（CJK 全角算 2 列），不用 text.length。

    大部分组件有缓存。Text 的 render（components/text.js）开头就是：

    render(width) {
  if (this.cachedLines && this.cachedText === this.text && this.cachedWidth === width) {
    return this.cachedLines;   // 文本和宽度都没变，直接命中缓存
  }
  // 换行 -> 加 padding -> 铺背景 -> 算出结果并写缓存
}

    缓存键就是「文本 + 视口宽度」。改文案要 invalidate()（setText 内部会顺手清理），宽度变了则天然重建。所以宽屏重排只要一条 resize 通知就够。

    Container 的 render 就是把子组件的行按顺序拼起来（tui.js 的 Container.render）。整个组件树，本质上是行数组的嵌套拼接。

    差分渲染

    TuiMainScreen.doRender（tui-main-screen.js）大致五步：

    1. 根组件 render(width) 得到新的行数组 newLines；
    2. 有浮层就先把 compositeOverlays 逐行叠进去；
    3. extractCursorPosition 找 CURSOR_MARKER，算光标位置并剥掉标记；
    4. 跟上一帧 previousLines 逐行做严格字符串比较，求出 firstChanged 和 lastChanged；
    5. 只重画变化区间：光标挪到首变化行，每行 \x1b[2K 清掉再写新内容，最后刷新 previousLines。

    几个细节：

    • 节流合并。requestRender() 只是把标志位置位，真正写屏由 scheduleRender 按 MIN_RENDER_INTERVAL_MS = 16ms（约 60fps）合并调度，一帧内调多次也只画一次。键盘输入走 requestImmediateRender()，用 process.nextTick 抢占节流，输入延迟比贴帧率更敏感（代码注释里提到 Windows 上 setTimeout(0) 都可能吃满 16ms）。
    • 同步输出防闪烁。每次渲染被 \x1b[?2026h（begin）和 \x1b[?2026l（end）包住，终端攒完一整批才刷屏。没有「画到一半的中间态」，自然不闪。
    • 什么时候整屏重绘。首次渲染、宽/高变化、内容收缩（clearOnShrink，可用 PI_CLEAR_ON_SHRINK=0 关掉）、首变化行滚出可见区。fullRedraws 计数和 PI_DEBUG_REDRAW=1 日志可以帮你查「为什么老在整屏重画」。
    • 分块写屏。一次渲染的输出可能很大，BoundedTerminalWriter 按 1MiB 分块，避免拼出超过 V8 字符串上限的单次 write，也不拆散代理对（emoji 安全）。

    输入链路

    ProcessTerminal.start（terminal.js）做的事：

    1. stdin.setRawMode(true) 进原始模式，开 bracketed paste（\x1b[?2004h），注册 resize。
    2. 向终端发 Kitty 键盘协议协商序列 \x1b[>7u\x1b[?u\x1b[c（消歧义 / 事件类型 / 备用键位三个 flag），支持就开 Kitty，不然回落 modifyOtherKeys。
    3. StdinBuffer 把字节流切成单个按键序列。转义序列按前缀累积；ESC 单独出现时得等一小段超时（本机 10ms，SSH 环境 100ms）再判定为 Escape，不然没法区分「按 Esc」和「Alt + 别的键」。

    事件到达 TuiBase.handleTerminalInput（tui.js）后：

    1. 先剥掉终端响应（OSC 11 背景色应答、配色方案报告、cell size 应答），这些不是按键。
    2. 依序调用 addInputListener 注册的监听器。{ consume: true } 短路；{ data } 改写原始数据再交给下一个。
    3. 没被消费的，交给 focusedComponent.handleInput(data)，然后在渲染帧层面决定重画。

    焦点与硬件光标

    Focusable 组件聚焦时要往渲染输出里埋一个零宽标记 CURSOR_MARKER（APC 序列）。渲染完 extractCursorPosition 从最底部可见行往上找，用标记前的 visibleWidth 算出列，剥掉标记，再 \x1b[<col>G 把硬件光标绝对定位过去。

    默认硬件光标是藏着的（hideCursor），位置照样定位。输入法候选框出现在正确位置，你看到的是组件自己画的假光标，更干净。少数终端不开可见光标 IME 就不干活，那就 setShowHardwareCursor(true) 或设 PI_HARDWARE_CURSOR=1。

    Overlay 合成

    浮层不进组件树，而是叠在一个 overlayStack 里（tui.js 的 showOverlay）。渲染时 compositeOverlays 按 focusOrder 排序，后弹的在上层，逐个布局：

    • width / maxHeight / row / col 支持数字或百分比，先扣 margin 再按 anchor 九个锚点定位，最后 clamp 进屏幕。
    • 浮层 render 出行后，compositeTuiLine 按列合入对应基础行。取基础行浮层区间前后的片段、截断浮层行、用 SEGMENT_RESET（顺带关掉 OSC 8 超链接）隔开再拼，两边 ANSI 不会互相污染。

    关浮层时焦点还给 preFocus（弹层时记住的那个组件）。TuiMainScreen 下没有干净位置放浮层时，先补空行把工作区撑到终端高度，再算 viewportTop 让浮层落进可见区域。

    终端能力协商与图片

    启动时 TUI 会问终端几件事：

    • CSI 16 t 查单元格像素尺寸，图片渲染要用；
    • ESC ] 11 ; ? BEL（OSC 11）查默认背景色；
    • CSI ? 996 n（DSR）查明/暗偏好，还能 setTerminalColorSchemeNotifications 订阅动态切换。

    Kitty 图片在 diff 里是特殊行：写屏前要删掉上一帧的旧 imageId（deleteChangedKittyImages），图片占多行，expandChangedRangeForKittyImages 会把整个图块纳入变化区间，避免重画一半花屏。这也解释了一个硬约束：任何一行的可见宽度都不能超过 width，超了直接抛错、写 pi-crash.log 诊断文件。

    底层机制值得记住的五个点：「行数组」是组件与渲染器的唯一协议；「文本 + 宽度」是缓存键，resize 自愈；「diff 区间 + 同步输出」保证不闪、开销小；consume / 改写的两级监听让全局快捷键跟组件自带按键不打架；埋标记、定位、剥离，是 IME 光标能落对的秘密。

    踩坑清单

    1. new TUI() 会报错。TUI 是接口，用 TuiMainScreen / TuiAltScreen，类型声明成 TUI。
    2. 改完状态记得 requestRender()，想强制就 renderNow(true)。
    3. 退出前先 loader.stop() 再 tui.stop()，Loader 有定时器。ProcessTerminal.drainInput() 还能挡住残留按键泄漏给父 shell。
    4. 组件是宽度驱动的，resize 自动重排，你通常不用管。
    5. 对齐别用 text.length，用 visibleWidth，全角字符算两列。
    6. VStack / HStack / ScrollView、鼠标滚轮、文本选区、搜索，只有 TuiAltScreen 有。
    7. Kitty 协议自动探测自动回落，不用你操心。
    8. 这个库迭代很快。demo 锁 0.84.4，升级后先 npm run check 过一遍类型。

    小结

    pi-tui 把终端 UI 抽象成组件树、差分渲染、输入路由三件事。写个聊天式的、设置式的命令行界面，基本不用再碰转义序列。想直接动手，拿 pi-tui-demo 当脚手架最快，把 main.ts 里的组件树换成自己的就行。
