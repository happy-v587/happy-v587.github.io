多轮对话里的
语义召回

「继续」「你改错了」「提交吧」——
query 只有五个字的时候，记忆还找得回来吗？

happy-v5872026 年 11 月
01 · 问题

一句「继续」，检索不到任何东西

Coding Agent 的连续交互里，越往后用户越省字

真实的四轮
用户修改登录模块的超时处理。
用户你改错了。
用户继续。
用户OK，提交吧。
每一轮 query 携带的信息
1模块 + 任务，完整
2没说明哪里错了
3没说明继续什么
4没说明提交哪些改动

第 2–4 轮的 query 缺「登录模块」「超时处理」这些主题词， 向量检索没有可对齐的语义——要么召回不到，要么召回到隔壁任务的记忆。

这是两个不同的问题：当前输入需不需要召回，以及现有信息够不够构造 query。

但语义完整也不等于一定命中正确记忆——这是两件事，别混在一起测。
02 · 现状

现在的 query 只有一个来源：本轮 prompt

缺口 写入端一轮一轮把完整对话存了进去，召回端手上只有这几个字—— 两边信息量差着一整段对话，中间没有任何补偿环节。
Recall Sufficiency Gate 在初次检索之后评估候选够不够，可触发有限扩展； 它不在召回之前判断 query 是否完整——位置不同，解决的不是这个问题。
调用方仍可自救 接口本身就接受任意字符串（上限 8192 字符），拼历史是允许的。 真正的问题是要不要由 PC 来做、做了靠不靠得住。
03 · 竞品

三个项目的差异，不在「存不存回复」

项目写入时存 assistant提取时用 assistant召回时用历史
PowerContextOpenCode 自动路径不存可参与提取只用本轮 query
mem0add / search调用方决定默认 infer 时用search 只用传入串
ovSession / search调用方决定异步提取可用带 session 做查询规划
存不存只是原料问题；真正决定效果的是补语义发生在哪一端—— 写入端补（mem0），还是召回端补（ov）。PowerContext 现在两端都没补。
03 · 竞品

ov 的做法：不判断完整性，直接改写 query

关键差别：它不是把几轮对话拼成一条长 query 再 embed 一次，而是用历史去生成检索计划。
03 · 竞品

mem0 把补语义放在写入端

add(messages)
读调用方传入的多角色消息
读近期消息窗口（默认保存有限条）
做模型提取，产出记忆条目

完整上下文在这里被消化成「记忆」。

search(query)
不读会话历史
不读最近消息
只做用调用方给的字符串检索

召回端依旧是短 query。

这个上下游不对称很有意思：提取端信息充分，召回端信息贫乏。 它是不是也值得在 Eval 里单独拉一组对照？
04 · 现状

各插件到底存了什么

集成用户输入助手回复说明
Claude Code、Codex✓✗只写入当前 prompt
DSH、Pi、OpenCode✓✗只写入当前 prompt
Kimi Code、ZCode、WorkBuddy、Cindy✓✗只写入当前 prompt
OpenClaw✓✗最近一条 user 文本
Hermes✓✓ 默认开启合并成一条 Source
Hermes：把两侧拼成一条资料
projected = f"[user]\n{user}\n\n[assistant]\n{assistant}"
capture(scope, sid, projected[:50000], {"kind": "hermes-turn"})

前 50000 字符截断；用户文本过长时助手内容会被挤掉； cron / subagent 不走这条路径；只是两段文本，不含工具调用与结果。

magpie：整段对话 JSON 塞进字符串
{"content": "{\"schema\":\"magpie.conversation
 .v1\",\"messages\":[...]}"}

content 是 1–200000 的纯字符串；服务端落进 MEDIUMBLOB， capture 时完全不解析，等处理管线提炼记忆时才当文本读。

05 · 方案

两条路：先判断再补，还是无脑补齐

方案 AJEV 按需判断

有判断成本；判断错了会静默走错分支。

方案 B固定补充最近 N 轮

简单、可复现，适合先做基线。

我的倾向：先用 B 建基线，再测 A 能不能带来足够收益——A 的价值要靠数据，不靠直觉。
05 · 方案

七个维度把 A 和 B 摊开

维度A · 按需判断B · 固定补充
语义完整的输入判断正确可直接用 query，不引入噪声仍附带历史，可能没必要
「继续」这类输入补前文，理论上还能决定补多少通常能补上，够不够取决于 N
历史噪声有机会只引入相关历史，但选哪些仍要设计最近 N 轮可能含已结束的任务
延迟与成本('较高：JEV 判断 + 可能多次', 'cell-bad')无额外调用，但文本更长
稳定性依赖判断质量；超时 / 波动要考虑('规则固定，易复现', 'cell-good')
实现复杂度判断 → 补充 → 再判断 → 上限 → 降级确定历史来源与截取范围
排查难度要区分判断错 / 选错历史 / 检索未命中先看拼进去的历史，再看结果
延迟和成本是预期方向，实际差异必须测——B 里文本变长带来的成本，也取决于检索通道和模型。
05 · 方案

两个方案各自怎么翻车

A 的风险判断错误
用户提交吧。

JEV 可能判为「完整操作指令」→ 不补历史。 但对召回来说，这句话没说提交哪个任务，仍然需要上下文。

用户你好

反过来，「你好」很简单，却不一定要检索历史记忆。 所以 A 的第一步其实要拆成两个问题。

B 的风险历史不相关或不足
用户数据库连接超时怎么处理？
助手……
用户现在修改登录页面的按钮颜色。

固定拼接后，检索文本同时含「数据库连接」和「按钮颜色」→ 召回隔壁任务。

另一种边界：任务目标出现在很早之前，最近 N 轮根本不够。

所以 A 要显式回答两问：① 当前输入要不要召回　② 要的话现有信息够不够构造 query。 这两问可以放在一个环节，也可以拆开——拆开更好排查。
06 · 边界

助手回复：能给出事实，也会给出幻觉

用户修复登录超时问题。
助手我发现超时配置在 auth/client.py，准备修改这个文件。
用户继续。
存下来的收益

只用用户输入，知道「在修登录超时」； 加上助手回复，还知道「涉及 auth/client.py」。这个文件名往往正是召回的关键锚点。

存下来的代价

「准备修改」是计划，不是已完成的事实。 助手判断错的时候，这段文本会被当成已验证结论反复召回。

无论 A 还是 B，只要用助手回复就必须保留说话角色，并区分 计划 推测 已验证结果。
07 · 验证

测试顺序：先立对照组，再谈优化

1
对照组
当前只用 query 的召回方式。所有后续对比都对着它。
2
方案 B · 扫历史范围
最近 1 / 5 / 10 轮分别测；消息条数与完整轮次必须分开定义。
3
方案 A · 单次判断
最多判断一次、补充一次，先看同样的测试集上有没有改善。
4
方案 A · 多次循环
只有第 3 步有明显收益才做。否则循环只是把延迟叠上去。
相关记忆召回率涨了多少
无关记忆增量噪声涨了多少
P95 延迟用户等多久
模型调用次数 / token每次对话多花多少
数据集要同时覆盖：「继续」这类依赖前文的输入、语义完整的输入、中途切换任务。
08 · 落地

三期推进：服务端先别动

第一阶段
插件实验
  • PC 服务端与现有接口不动
  • 选一个能拿到宿主历史的插件
  • 插件侧拼 query，调 prepare_context
要回答：宿主能给哪些历史？含不含助手回复？取几轮？
第二阶段
Eval 评估
  • 构造多轮对话集，标注期望召回
  • 三路对照：当前 query / 固定 N 轮 / 动态改写
  • 走现有召回链路，只换 query 构造方式
要回答：相关召回、无关增量、延迟、成本各是多少？
第三阶段
服务端能力
  • 仅在前两阶段有数据支持时启动
  • 参考 ov，考虑新增带会话的召回入口
  • 固定轮次与动态选择两种策略并存
要回答：历史由调用方传还是 PC 读？长度上限？降级方式？
