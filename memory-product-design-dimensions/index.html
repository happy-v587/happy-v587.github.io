    Memory 产品设计：输入、计算与产物的排列组合

    2026-11-22 · 发布于 文章 · 4453 字 · 9 分钟
    • AI
    • Memory
    • AI Agent
    • 产品设计
    • 知识管理

    上一篇文章《Memory 系统设计的一些要领》讲的是技术侧：写入怎么对账、召回怎么融合、评测怎么做、平台怎么治理。那回答的是"能不能做"。

    但技术要领不等于产品。同一个 Memory 引擎，换一个输入源、换一种计算深度、换一个产物形态，就会长成完全不同的产品。很多 Memory 产品用起来别扭，不是模型不够强，而是这三个维度没有对齐：用做个人记忆的轻计算去接企业知识库，或者用企业级的重计算去处理用户的一句闲聊。

    这篇文章换一个视角，从产品维度拆 Memory：原始输入、中间计算、最终产物。三者不是流水线上的三个步骤，而是一个可以排列组合的产品空间。

    一、产品公式：输入 × 计算 × 产物

    可以先写一个很粗略的公式：

    Memory 产品 = 输入域 × 计算深度 × 产物形态 × 触发方式

    四个变量分别回答：

    • 输入域：谁产生的数据，什么模态，多大规模，权限归谁；
    • 计算深度：原文直存，还是抽取、综合、生成、后台再加工；
    • 产物形态：可检索的记忆、结构化画像、可直接消费的文档或 Skill、主动触发的动作；
    • 触发方式：写入时算、查询时算、定时算，还是事件驱动。

    这四个变量相互约束。输入模态决定能不能算、算不算得起；计算深度决定产物的新鲜度和可信度；产物形态决定怎么评测；触发方式决定用户等不等得起。

    产品设计的第一步，不是选模型，而是把这四个格子填清楚。

    二、原始输入：不是"一段文本"，而是四组约束

    谈输入时，很容易只说"文本、图片、音视频"。但真正影响产品设计的，是下面四组约束。

    2.1 来源

    • 用户的一句话；
    • 用户和 Agent 的一段会话；
    • 企业的知识库、群消息、文档、会议、工单；
    • 个人散落在各个应用里的数据：照片、购物记录、心愿清单、日历、家庭成员。

    来源不同，采集方式、更新频率、权限模型完全不同。企业知识库是持续变化的，个人数据是碎片化的，Agent 会话则是天然按 session 组织的。

    2.2 模态

    不同模态的处理目标，不是"统一变成一段文本"，而是保留后续计算需要的信息。

    模态处理策略容易丢的信息
    纯文本清洗、去噪、按语义或结构切块来源、时间、上下文
    富文本保留标题层级、表格、链接、代码块结构一旦拍平，关系和层级就没了
    音频/视频ASR、说话人分离、时间戳、分段摘要语气、停顿、谁在说
    图片OCR、视觉描述、EXIF、时间地点画面里的对象关系和场景
    结构化数据保留 schema，做规则聚合和关联硬转成自然语言后，数值和字段含义会失真

    一个常见错误是：入库时把所有东西都压成纯文本，等到要做项目画像或偏好推断时，才发现标题层级、表格字段、消息发送者这些信息已经丢了。输入处理要服务于下游计算，而不是只服务于存储。

    2.3 体量与速度

    一句话和 TB 级知识库，不能用同一套链路。前者适合同步、轻量、即时反馈；后者必须增量同步、批处理、异步回执。输入规模直接决定了计算能不能放在请求路径里。

    2.4 权限与归属

    输入是有主人的。个人数据属于个人，群消息属于群，企业文档继承企业权限。产物必须继承输入的权限，否则聚合做得越好，越权风险越大。

    这一条在个人场景里容易被忽略，在企业场景里则是生死线。

    三、中间计算：一条从 L0 到 L4 的阶梯

    计算不是"要不要用 LLM"的二元选择，而是一条从轻到重的阶梯。越往下，成本、延迟、不可解释性越高，但产物越接近"可以直接行动的知识"。

    层级做什么典型产物成本与延迟适用场景
    L0 直存原文或原文件落库，建立索引原始证据低合规留档、可重算、证据链
    L1 抽取事实、偏好、经验、实体、标签记忆条目中Agent 记忆、个人助手
    L2 综合项目 Topic、Profile、时间线、状态结构化画像高企业项目知识、客户画像
    L3 生成Skill、Handoff、Runbook、报告可直接消费的文档很高工作交接、培训、自动化
    L4 再加工纠错、合并、补全、遗忘更干净的记忆库周期性长期运行的系统

    L0：不计算也是一种策略

    原文直存不是"偷懒"，而是一种产品选择。合规、审计、法律取证这类场景，需要的恰恰是未经加工的原始证据。即使上游有抽取，L0 也应该作为安全网保留：抽取器升级、prompt 调整、模型换代之后，还能回到原文重算。

    L1：事实、偏好、经验

    这是大多数 Agent Memory 产品的主战场。三类内容的难度不同：

    • 事实：相对客观，抽取和校验都容易；
    • 偏好：显式偏好好办，隐式偏好难，而且会随时间变化；
    • 经验：往往藏在"怎么做成的"过程里，单轮抽取容易丢上下文。

    L1 的关键不是抽得多，而是抽得准，并且知道什么不该抽。一次性意图、临时状态、操作日志，进入长期记忆后都是噪声。

    L2：从碎片到画像

    当输入从"一段会话"变成"多个文档、多个群、多个项目"时，计算的重点会从抽取转向综合：

    • 实体对齐：同一个项目在文档、群名、工单里可能有不同叫法；
    • 时间线：哪些是当前状态，哪些是历史决策；
    • 冲突处理：不同来源说法不一致时，以谁为准；
    • 权限裁剪：不同的人看同一个项目，画像的可见范围不同。

    L2 的产物通常不是"一条记忆"，而是 Topic、Profile、项目状态这类结构化对象。它的难点不在生成，而在持续更新和可解释。

    L3：从记忆到可执行产物

    再往上，产物会变成 Skill、Handoff、Runbook 这类"可执行知识"。

    它们和记忆的区别在于：记忆回答"是什么"，Skill 回答"怎么做"，Handoff 回答"接到哪了、下一步是什么"。所以 L3 不能只做摘要，还要保留：

    • 前置条件与适用范围；
    • 关键决策和放弃的方案；
    • 未解决的问题与下一步；
    • 责任人和时间。

    这也意味着 L3 的评测不能只看"像不像"，还要看人能不能照着做、Agent 能不能照着执行。

    L4：再异步，Dream 与后台整理

    写入和查询之外，还有第三层时间尺度：周期性或事件触发的后台任务，对已有记忆做纠错、合并、摘要、遗忘。业界常用 Dream、reflection、consolidation 这类说法。

    它解决的是"一次性抽取"解决不了的问题：

    • 两条记忆其实在说同一件事，需要合并；
    • 新事实推翻了旧结论，需要纠正；
    • 一串零散事件可以归纳成一条经验；
    • 长期不用的记忆应该降权或遗忘。

    Dream 很有价值，但也有明显风险：后台加工同样可能产生幻觉。所以它需要证据链、变更记录和可回滚机制，不能变成一个黑盒的"记忆重写器"。

    同步、异步、再异步

    计算放在哪一层，取决于用户等不等得起：

    • 同步：用户在线等待，只做轻量解析、规则抽取、简单 embedding；
    • 异步：LLM 抽取、跨文档综合，先返回回执，完成后再通知；
    • 再异步：Dream 按时间、写入量或事件触发，做全局整理。

    一个实用的原则是：交互路径只做"必须现在做"的计算，其余全部后移。 但后移不等于不管，异步任务要有状态、重试、幂等和可观测。

    四、最终产物：三种消费者，三种投影

    同一份记忆，可以被三类对象消费，而它们的要求完全不同。

    4.1 给 Agent 消费

    产物是注入上下文的记忆片段。要求是短、准、结构化、低延迟。评测看的是任务成功率、召回精度、token 效率和上下文占用。

    这类产物的核心问题是"取多少"：取少了不够用，取多了污染上下文。所以检索、重排、预算控制比生成更重要。

    4.2 给人消费

    产物是项目画像、交接文档、周报、Skill。要求是可读、可追溯、可行动、足够新鲜。评测看的是人能不能理解、敢不敢信、能不能照着做。

    这类产物需要来源引用和更新时间。没有出处的总结，在企业场景里很难被真正采用。

    4.3 给系统消费

    产物是触发器、提醒、推荐。比如"谁快过生日了"“该补货了"“这个项目风险升高了”。要求是准确、及时、可解释，并且尊重用户的注意力。

    评测看的是主动命中率和打扰率。一次错误推荐的成本，可能高于十次正确推荐带来的价值。

    一份存储，多种投影。 不要指望用一个接口同时满足 Agent、人和系统。产物形态不同，接口、刷新策略和评测方式都应该不同。

    五、三个典型产品原型

    把三个维度组合起来，会得到不同的产品。下面是最常见的三种。

    5.1 个人 Coding Agent 记忆

    维度选择
    输入用户 query、过去的 session、仓库上下文
    计算L1 抽取与总结
    产物Automatic Memory，注入后续会话
    关键指标任务成功率、延迟、上下文 token

    这是最小可行的组合：session 进来，总结成事实和偏好，下次会话召回。产品重点是低延迟、少配置、可删除、不过度记忆。失败模式通常不是"记不住”，而是"记得太多太旧"，把上下文挤满。

    5.2 企业办公与项目知识

    维度选择
    输入知识库、群消息、文档、会议、工单
    计算L2 综合，辅以 L1 抽取
    产物项目 Topic、Profile、决策记录、Handoff
    关键指标覆盖率、权限正确率、新鲜度、人工采纳率

    企业场景的难点不在模型，而在数据治理：增量同步、实体对齐、权限继承、来源追溯、冲突处理。产物往往需要人参与确认，不能完全自动生成后就发布。

    失败模式也很典型：权限泄漏、画像过期、多个来源互相矛盾、摘要的摘要丢掉了关键细节。

    5.3 个人 Agent

    维度选择
    输入照片、购物记录、心愿清单、日历、家庭成员、聊天记录
    计算L2 画像 + 事件检测，必要时 L3/L4
    产物主动提醒、推荐、待办
    关键指标主动命中率、打扰率、隐私合规

    个人 Agent 的产品重点不是"知道得多"，而是"在正确的时机做正确的事"。它需要 consent、可解释、可关闭，还需要一个打扰预算。推断错一次，用户可能就再也不想用了。

    六、排列组合时最容易踩的坑

    1. 输入和计算错配。用 L1 处理企业知识库，会得到一堆碎片，缺少全局；用 L4 处理一句话，则是过度计算，成本和延迟都不划算。
    2. 产物和消费者错配。给 Agent 的产物要求短而准，给人的产物要求可读可追溯，给系统的产物要求可触发可解释。混成一个接口，三方都不满意。
    3. 同步链路做重计算。用户等不起。重计算应该异步化，但要有状态、回执和超时。
    4. 忽略权限继承。输入有权限，产物也必须继承。聚合和摘要是越权的高发区。
    5. 没有遗忘机制。只增不减，产物会越来越旧、越来越吵。遗忘和降权应该是一等公民。
    6. 把 Dream 当万能。后台再加工能提升质量，也会引入幻觉。没有证据链和回滚，就不要让它自动改写重要记忆。

    七、第一个产品怎么选

    可以用五个问题快速筛：

    • 输入是否已经数字化、可访问、权限清晰？
    • 产物主要给 Agent、给人，还是给系统？
    • 用户愿意等多久？
    • 产物错了的代价有多大？
    • 有没有反馈闭环，能让系统越用越准？

    如果输入零散、权限复杂、错误代价高，先从 L0/L1 做起，把证据和基础记忆打牢；如果输入已经结构化、消费者明确，可以直接做 L2/L3，用产物价值拉动数据治理。

    技术要领回答"能不能做"，产品维度回答"值不值得做、先做哪一个"。同一套 Memory 引擎，换一个输入、换一层计算、换一种产物，就是另一个产品。
